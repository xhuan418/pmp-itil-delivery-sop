# PMP & ITIL Delivery SOP

Turn PMP project-governance concepts and ITIL 4 service-management concepts into practical, proportionate routines. Optimize for clear outcomes, ownership, decisions, communications, records, and service continuity - not bureaucracy.

## Workflow

1. Identify the lifecycle phase and classify the request: project, service request, incident, problem, change, transition, or continual improvement.
2. Confirm desired business outcome, affected customers/users, material constraints, decision owner, and risks. Do not invent approvals, budgets, deadlines, service targets, or contractual commitments.
3. Use the smallest relevant set of artifacts and routines. Read [references/lifecycle-sop.md](references/lifecycle-sop.md) for phase checklists, routes, and templates.
4. Clearly separate recommendations from approved commitments. Require the appropriate authority for material scope, schedule, cost, service, contract, or compliance changes.
5. In customer-facing output, state impact, options, recommendation, decision owner, and next update time when relevant.

## Help the user apply the SOP

This skill is an operating method, not a form that the user must complete before getting help. Act on the facts already supplied and ask only for information that materially changes the recommendation.

- If the request is sufficiently clear, give the recommendation and smallest useful artifact immediately.
- If the request is broad, first explain the relevant lifecycle route, minimum useful inputs, and one copyable prompt. Do not require the user to read every template.
- If key facts are absent, state assumptions and ask focused follow-up questions; do not invent authority, commitments, deadlines, or constraints.
- When useful, offer a ready-to-copy prompt tailored to the user's situation.

Read [references/using-this-skill.md](references/using-this-skill.md) when the user asks how to invoke the skill, needs prompt help, or has an incomplete situation.

## Select management tools by decision need

Do not give the user a generic catalogue of PMP tools or recommend a tool just because it is well known. First identify the management question: are they clarifying scope, estimating, detecting a schedule/cost variance, diagnosing a cause, prioritizing work, controlling a change, communicating status, or improving service?

Read [references/management-tool-selection.md](references/management-tool-selection.md) when the user asks which table, chart, technique, or metric to use; when schedule/cost/quality performance is off plan; or when they need to analyse rather than merely report a project problem.

Choose the lightest tool that supports the decision. State the input data required, what the output can and cannot prove, and the next management action. Do not calculate or rely on EVM, velocity, critical path, or trend forecasts when their necessary baseline/data are missing or unreliable.

## Decision rules

- Future uncertainty is a **risk**; current interruption/failure is an **issue or incident**.
- Pre-defined repeatable demand is a **service request**; a controlled addition, modification, or removal is a **change**.
- Route uncommitted agile needs to the backlog for product-owner prioritization. Use formal control for changes to governed baselines, commitments, or service configuration.
- Restore a critical service before full root-cause analysis. Create/link a problem record for recurring or major incidents.
- Use direct, transparent communication and collaborative problem-solving before escalation. Escalate when authority, risk tolerance, resources, contract, compliance, or cross-team priorities require it.

## Output standards

- Start with the immediate outcome and recommended next action.
- Label assumptions, open decisions, risks, and decisions requiring approval.
- Reuse the repository templates when they fit; preserve the user's terminology and actual governance.
